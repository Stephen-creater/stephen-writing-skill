# 实践指南与避坑

## 适用

团队实践、工作流、治理机制、最佳实践和避坑指南。

## 写法

- 文章由具体产品或官方实践触发时，标题直接写明对象和读者能获得的价值，第一节解释它带来了什么变化。
- 教程或工作坊浓缩稿可以保留原有知识顺序，但每节只留一个核心机制和一个不可替代的案例或边界。
- 小标题并列两个概念时，必须同时写出两者的功能；如果本节只解释其中一个，就拆开或改名。
- 可以用编号组织，但来源中的经验数量不决定正文结构。只保留能组成当前主线的原则，其余整条删除。
- 两条原则存在直接依赖时合并讲。例如 Agent 先看见团队上下文，再在共享空间里明确分工。
- 每一点都要有明确结论，并说清原因、案例或操作方法。一个案例已经证明判断时，不再追加同类案例。
- 数字型框架先筛选真正影响行动的标准，再确定「4笔账」「3个问题」。标题数字、章节和结尾问题必须一一对应。
- 多标准框架可以每节换一个案例，但每个案例只服务当前标准。案例写清旧流程、业务代价和理想变化，再用一句话收成判断。
- 标题写清服务对象和决策时点，例如「FDE 做 Demo 前」，不要把所有企业 AI 问题都装进一篇文章。
- 把经验落到可查对的机制：输入输出、触发条件、权限、共享空间、角色、目标、Owner 和测试。
- 具体数字只在有经验或证据时使用，不用精确数字制造专业感。
- 结尾回到组织、业务或用户最终会发生什么，不复述前面的步骤。
- 文末原文信息只留作者的必要身份、原文直链和必要的时间信息。履历不影响正文判断时删除。

## 避免

- 只给原则，没有可执行做法。
- 把特定公司的情况写成所有团队的统一规则。
- 用工具名、文件夹和专业词数量代替真正治理。
- 为了凑整数，保留一条正确但不影响当前行动的标准。
- 保留直播、访谈或课程的现场旁白，拖慢进入案例的速度。
- 机制已经由一个工作案例讲清后，又保留一个有趣但没有新变量的生活案例。
- 为了显得完整，把官方原文中的每一条经验都保留下来。
- 删掉产品、发布或事件本身，只剩一篇脱离时间背景的通用方法论。
