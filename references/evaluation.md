# 评测：改了 Skill 之后，文章有没有变好

每次改 Skill（规则、范文、脚本里影响写作的部分），都要证明新版本写出来的初稿，比旧版本更接近 Stephen 会发的样子，至少不更差。评测不看文档写得规不规范，只看写出来的文章。

## 为什么这样设计

写作没有标准答案，但 Stephen 有：他发布出去的那一版。所以评测拿他已发布的文章当参照，看新旧两版 Skill 写出的初稿，哪篇离参照更近、他改起来更省力。做法参考了业界评测写作模型的常用做法：

- **固定题库**：每道题是 Stephen 当时给的要求、原始材料和他的发布版。题库不变，不同版本的分数才能比。
- **盲评、两两对比**：评委只看到 A、B 两篇，不知道哪篇是新版。比起给单篇打绝对分，两两比较更稳定。
- **换位置评两次**：评委容易偏向排在前面的那篇，所以每道题两位评委各评一次，A、B 位置互换。
- **先校准评委**：让评委在不知情的情况下，从 Stephen 发布版和历史 Agent 初稿里挑更好的一篇。评委挑不出 Stephen 那篇，说明它的口味和 Stephen 不一样，它打的分就不可信，要先改评委说明。
- **开发集和留出集分开**：题库分两份。开发集可以拿来找问题、改规则；留出集平时不看，规则里也不能引用留出集的文章。开发集变好、留出集变差，说明规则只是记住了那几篇文章。
- **月光宝盒**：每个通过评测的版本打一个 git 标签，标签名和评测时的版本名一致（例如 `writing-v1`、`writing-v4`），每次评测写出的初稿和评委结果都存档。随时可以把两个旧版本拿出来对比，也可以一键恢复到某个旧版本。

## 文件在哪

全部在 `<日课创作>/评测/`，只在本机，不进 Git（里面有付费文章全文）。

| 位置 | 是什么 |
|---|---|
| `题库/<题目>/要求.md` | Stephen 当时给写稿 Agent 的要求 |
| `题库/<题目>/材料/` | 当时给的原始材料 |

| `运行/<版本>/` | 某个版本在每道题上写的初稿、交付说明，以及当时用的 Skill 副本 |
| `历史.jsonl` | 每次评测的结果 |

## 怎么跑

在 `<日课创作>` 目录下：

```bash
# 1. 给要比较的两个版本准备写作任务（旧版用标签或提交号，新版用当前工作区）
python3 stephen-writing-skill/scripts/eval_writing.py prepare v4 --ref writing-v4
python3 stephen-writing-skill/scripts/eval_writing.py prepare v5
```

2. 每道题开一个新的写稿 Agent，只让它读 `运行/<版本>/<题目>/任务.md` 并照做。任务里写明了只能用哪份 Skill 副本、不能读哪些目录（副本里已经删掉这道题自己的范文，防止照抄答案）。在 Claude Code 里用 Workflow 并行跑；在 Codex 里用子 Agent 或逐个会话跑。

```bash
# 3. 生成盲评任务，每道题两份，A、B 位置互换
python3 stephen-writing-skill/scripts/eval_writing.py pairs v4 v5
```

4. `评测/对比-v4-vs-v5.json` 里每一项交给一个新开的评委 Agent，让它按下面的「评委说明」判断，结果收集成一个 JSON 数组，每一项在盲评任务的基础上加上 `winner`、`effort`、`coverage`、`flags`、`reason`。

```bash
# 5. 汇总并判断能不能上线
python3 stephen-writing-skill/scripts/eval_writing.py score 评测/结果-v4-vs-v5.json --new v5 --stamp 2026-09-20
# 6. 通过就提交，并打标签（标签名用评测时的版本名）
git tag writing-v5
```

题库、评委说明改了之后，先跑一次校准（`calibrate` 生成任务，交给评委，再 `score`），看评委还能不能挑出 Stephen 的发布版。

## 什么时候值得跑评测

跑一轮要几十个 Agent 和十分钟，不是每次改动都值得。按这个来：

| 情况 | 怎么办 |
|---|---|
| Stephen 明说的要求（以后都这样、这次别这么写） | 直接改，不用测。他说了算 |
| 我自己想出来的小改（加一条检查、换个说法） | 先攒着。等攒够几条，或者下次大改时一起测 |
| 能用脚本确定性解决的（字数、标点、数字核对） | 写进脚本，不靠 Agent，不用测 |
| 大改：重写规则、换结构、换写作步骤 | 全跑 |
| 怀疑某一版变差了 | 全跑，和上一个通过评测的标签比 |

日常最便宜也最真实的信号，是每篇真实写的稿子：

```bash
python3 stephen-writing-skill/scripts/edit_ratio.py work/某篇初稿.md "已发布文章/第十周__某篇.md" --title 某篇
python3 stephen-writing-skill/scripts/edit_ratio.py --show
```

它算三个数：初稿被删掉多少、发布版里有多少初稿已经写到、长度比。不用开任何 Agent。历史 9 篇的基线是平均删掉 60%、发布版已写到 77%。以后每篇发布后记一行，趋势比任何一次评测都实在。09-21 的两篇：《吾辈如神》Agent 重构版被删 39%、已写到 75%（这版是在 Stephen 合并稿上重构的，不能直接和历史比）；《AI 越强越忙》Agent 初稿到 Stephen 改版（未发布）被删 25%、已写到 78%；《剪映 Hub》被删 16%、已写到 90%，是目前改得最少的一篇。

## 改了哪一层，就只测哪一层

一轮全跑要 65 个 Agent、约 10 分钟。多数改动不必全跑：

| 改了什么 | 怎么测 | 要几个 Agent |
|---|---|---|
| 写作指南、分类说明、范文、SKILL.md 的写作步骤 | 全跑：重新起草、审稿、修改，再盲评 | 约 65 |
| 只改审稿指南 | `prepare 新版本 --reuse-drafts 旧版本`，复用同一批未审初稿，只重跑审稿和修改，再盲评 | 约 52 |
| 只改评委说明 | 不重写稿子，拿现有两版初稿重判一次，再跑一次评委校准 | 约 39 |
| 只改脚本、文档、注释，不影响写作 | 不用测，跑一遍脚本自检就行 | 0 |

复用未审初稿还有一个好处：两版从同一篇稿子出发，差别只来自审稿，不掺起草的随机波动，小改也测得出来。

## 多小的改动测不出来

13 道题、每道写一次，胜率的随机波动大约 0.15。这意味着：

- 只有大改（影响每篇稿子的写法）才能靠全跑测出来。
- 小改要么攒几条一起测，要么用上面的复用办法做配对测试。
- 单独一道题的输赢基本没有意义，看整体。
- 题库扩大以后，每个版本每道题写两次取平均，能把波动压到一半左右。

## 上线标准

- 开发集：新版胜率至少 0.5（平局算半场）。
- 编造：新版被评委标出「编造」的次数不能比旧版多。
- 留出集：新版胜率不低于 0.45。
- 同时看两份清单：新版输掉的题（为什么输），以及评委标出的问题。数字过线但某道题输得很惨，也要先看原因。

`score` 还会算两个不靠评委的数字，只作参考：初稿里有多少文字没出现在发布版里（Stephen 大概要删多少），发布版里有多少内容初稿已经写到了。

## 历次结果

题库 15 道：开发集 9 道，留出集 6 道（09-21 加入《吾辈如神》，两份播客逐字稿合成一篇，Stephen 自己改过一版再由 Agent 收尾；加入《剪映 Hub》，定稿是他贴回来的终稿，发布后再用同步下来的版本换掉 定稿.md）。每道题两位评委、A/B 互换，胜率里平局算半场。

| 版本 | 改了什么 | 开发集胜率 | 留出集胜率 | 结论 |
|---|---|---|---|---|
| writing-v1 | 09-19 改版前的旧版，作为基线 | 对照 | 对照 | 基线 |
| v2 | 合并规则、写审分开、覆盖率和字数不设默认 | 0.44 | 0.13 | 没通过：把原文句子全改写了、内容包成「某某认为」、具体细节被概括掉 |
| v3 | 默认改编不重写、材料观点直接讲、细节照原文留、不单开「怎么试」 | 0.89 | 0.63 | 没通过：一处数字抄错（5%–10% 写成 10%） |
| **writing-v4** | 审稿逐个核对数字、人名 | **0.72** | **0.50** | 上线 |

v3 和 v4 的规则只差审稿指南里一句话，胜率却差了 0.15 左右，这是写稿本身的随机波动。所以单道题的输赢不要过度解读，看整体；题库扩大以后，每道题可以写两次取平均。

评委校准：第一次只有 9/13 挑中 Stephen 的发布版，评委偏爱内容更全的长稿，还把 Stephen 自己补的背景当成编造。按「删东西快、补内容难」「作者补充不算编造」改了评委说明后，第二次 23/26。

注意：v2 输掉后，为了找原因看过留出集的评委意见，所以留出集已经被用过一次。新发布的文章找回材料后，优先补进留出集。

## 月光宝盒：恢复旧版本

```bash
git tag --list 'writing-v*'                                   # 看有哪些通过评测的版本
python3 stephen-writing-skill/scripts/eval_writing.py history  # 看每个版本的成绩
python3 stephen-writing-skill/scripts/eval_writing.py restore writing-v1
```

`restore` 只改工作区，不自动提交。确认要用旧版，再按 AGENTS.md 提交并同步；不想要就 `git checkout HEAD -- stephen-writing-skill` 回到当前版本。

## 题库怎么扩充

写稿时按 SKILL.md 第 6 步存过材料，这一步就很省事：

```bash
python3 scripts/sync_published.py                    # 从飞书同步最新发布版
python3 stephen-writing-skill/scripts/add_case.py doubao \
    --materials work/材料/豆包工作 \
    --draft work/doubao-work-feishu-guide-draft.md \
    --final "已发布文章/第五周__8.26 字节「豆包工作」重磅发布.md" \
    --category AI热点与产品发布 --example "AI热点与产品发布/8.26 字节「豆包工作」重磅发布.md"
```

新题默认进留出集，因为它没参与过改规则。加完重新跑一遍当前版本，把这道题的成绩补上。

老文章也能补：材料能从 `work/`、Codex 附件或会话记录里找回来就行。找不回材料的文章进不了题库。

## 评委说明

你是中文 AI 日课文章的评委。Stephen 是作者：他把要求和材料交给写稿 Agent，拿到初稿后自己动手改成发布版。

你会拿到：要求、材料、参照稿（Stephen 的发布版；校准时没有）、两篇初稿 A 和 B。

有参照稿时，先读参照稿，列出它的 5 到 8 个核心要点（只算材料里有依据的内容，Stephen 自己补充的知识不算），再读 A、B。判断哪篇更接近参照稿会发出去的样子、Stephen 改起来更省力。没有参照稿时，判断哪篇作为发给普通读者的日课更好。

- Stephen 的口味：一条线讲透，枝节删得狠。一个判断成立后，只留最能说明问题的一个细节或案例。内容更全不等于更好。
- Stephen 删东西很快，补内容、改结构、改视角、核事实很费劲。估计改稿力气时，多出来但方向对的内容只算小改；缺了关键内容、方向偏了、视角错了才算大改。有参照稿时，按这个力气判胜负。
- 编造只算三种：和材料矛盾；虚构亲历、实测、采访；凭空写出数据或引语。Stephen 自己补的背景、常识、类比和判断不算编造。
- 忽略图片占位、飞书格式残留、链接写法这类排版差异。
- 真的难分高下才判平局。

逐篇给出：

- `effort`：1 到 5。有参照稿时是从这篇改到参照稿要花的力气；没有时是离能发布还差多少。1 是几乎直接能发，5 是要推倒重写。
- `coverage`：0 到 1，参照稿核心要点被这篇覆盖的比例。没有参照稿时填 0。
- `flags`：这篇明显存在的问题，只能从下表选，没有就留空。
- `reason`：两三句话，具体说到哪一段、哪句。

| 问题 | 什么样算 |
|---|---|
| 重复 | 同一个意思换说法又讲一遍，或案例后面补总结 |
| 视角 | 该用「我」的地方退成旁观者（开发者、用户），或没有亲历却写成我实测 |
| 看不懂 | 术语没解释、「这个」「那个」找不到指向、依赖看不到的图、跳步 |
| 顺序 | 东西在读者遇到之前就出场，或段落之间接不上 |
| 编造 | 和材料矛盾，或虚构亲历、实测、采访、数据、引语 |
| 开头慢 | 铺垫两句以上才进入正题 |
| 结尾空 | 结尾复述全文、喊口号或临时拔高 |
| 堆案例 | 同一个判断用了两个以上同类案例 |
| AI腔 | 引号破折号很多、「不是 X 而是 Y」、「值得注意的是」这类套话 |
| 漏重点 | 参照稿里有、材料里也有依据的核心内容，这篇没有 |

输出 JSON：`{"winner": "A" | "B" | "tie", "effort": {"A": 1-5, "B": 1-5}, "coverage": {"A": 0-1, "B": 0-1}, "flags": {"A": [...], "B": [...]}, "reason": "..."}`
