# Stephen Writing Skill

这是 Stephen 在「日课创作」项目内持续维护和使用的个人写作 Skill。它用于根据 Stephen 的既有文章风格，撰写、整合和修改 AI 热点、产品评测、概念解释与实践指南。

## 最重要的写作原则

- 标题规定文章最终抵达的位置。
- 具体产品或事件是选题成立的原因时，标题或第一节必须保留这个现实锚点。
- 全文只走一条主路径。观点文走因果链，产品速览走使用路径，数字型业务框架走一组共同决定是否行动的检查项。
- 正确、精彩、信息量大的内容，也可能因为不推动主线而被整节删除。
- 协议和标准类热点优先写成「是什么、怎么工作、当前边界」；案例只重演机制时不保留。
- 来源列出几条经验，不代表正文必须保留几条；相邻原则可以合并，旁支可以整条删除。
- 数字型标题是一份结构合同，标题数字、章节数量和结尾问题必须逐一对应，不能为了凑数保留支线。
- 观点文章可以从负面诊断改成行动框架，但标题、小标题和结尾必须一起重构，不能只换包装。
- 标题同时写明时间、读者和答案时，正文只保留会改变这类读者判断的机会、优势和行动。
- 一个意思只说一次，换一种表述仍然算重复。
- Aha moment 由正文的逻辑闭合产生，结尾不临时制造高潮。
- 正文默认不用引号；确实需要时只用「」。尽可能不用破折号。
- 开头零句或一句。标题已经说清对象时，可以直接进入第一个小标题。
- 产品速览的小标题可以直接导航到入口、功能和价格，不强行写成观点。
- 用户明确指定原文覆盖率时，以本次数字为准；默认验收线只用于没有单独约定的任务。
- 面向小白时，不保留需要额外专业背景才能看懂的案例。
- 业务框架每节只留一个主要案例，案例结束后直接收成可检查的判断标准。
- 自有企业案例只保留能证明方法的数字、周期、业务场景和结果，不带人物包装与服务宣传。
- 强比例和极端数字必须单独核验；案例用于学习写法，不自动成为事实来源。
- 翻译稿优先改成自然中文，不使用「是 X，不是 Y」等翻案句。

## 目录

- `SKILL.md`：AI 使用的入口、分类路由和工作流程。
- `references/voice.md`：作者的语气、解释方式、论证习惯和节奏。
- `references/check_standards.md`：交付前必须执行的检查标准。
- `examples/`：按文章类型分类的定稿案例与分类标准。
- `scripts/save_draft.py`：用户确认定稿后使用的存档脚本。
- `scripts/check_style.py`：检查正文中的引号和破折号。

## 建议阅读顺序

1. 先读 `SKILL.md` 的「最高优先级」和工作流。
2. 再读 `references/voice.md` 与 `references/check_standards.md`。
3. 根据要写的文章类型，只读对应分类的 `standards.md` 和一至两篇最终案例。

## 原文整合

用户授权整合原文时，连续 30 字覆盖率默认以 80% 为正常验收线。用户明确指定其他数字时按本次要求验收；没有单独约定时，70% 只用于修正事实、补齐缺失图片信息或维持完整逻辑等确有必要的情况。

## 版本管理

Skill 的更新先在「日课创作」项目 Git 仓库中提交，再同步到公开仓库 `Stephen-creater/stephen-writing-skill`。公开同步由父项目维护脚本负责，该脚本不属于公开 Skill。未经确认的初稿保留在项目 `work/` 目录，不直接进入案例库。
